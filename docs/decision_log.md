# 项目决策日志（Decision Log）

> 本文件记录项目各阶段关键决策的选项、判断与理由，体现项目演进中的思考过程。
> 决策由项目成员赵伟翔、周恒毅讨论确定，AI 工具（Kimi / WorkBuddy）仅作为建议与执行辅助。

## 阶段一（2026-10-16 ～ 2026-10-19）

| # | 决策                      | 当时的选项                                                 | 我们的判断与理由                                                                                                  |
| - | ----------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1 | 工作方式：双 AI 工具分工          | A.Kimi 负责规划与验收 + WorkBuddy 负责编码；B. 只用一个 AI 工具；        | 选 A。8.4 GB 的数据让我们意识到任务必须先被拆解才能动手。规划与验收由我们（借助 Kimi）把握，代码执行交给 WorkBuddy，两边上下文各自保持干净，且每一步产出都经过我们运行核对         |
| 2 | 选题：预测投诉处理结果（三分类）        | A. 叙述文本分类；B. 救济结果预测；C. 投诉量时间序列                        | 选 B。叙述文本字段大量缺失（需投诉人同意才公开），文本分类的可用数据缩水且我们难以判断其结果好坏；时间序列的预测目标不够明确。救济结果预测的输入输出都有明确的业务含义——我们选择我们能理解、能用常识验证的方向 |
| 3 | 评估指标：宏平均 F1             | A. 准确率；B. 宏平均 F1                                      | 选 B。多数类占 63.6%，永远预测多数类准确率就有 0.64，准确率在该任务上没有区分度。宏平均 F1 对每个类别一视同仁，能暴露模型在稀有类上的失败                             |
| 4 | 金钱救济类（1.4%）的定位          | A. 视为数据质量问题尝试规避；B. 视为研究价值                             | 选 B。稀有但重要的类别正是简单规则失效、值得系统研究的地方。它直接决定了指标选择和后续阶段的改进方向                                                       |
| 5 | 采样策略：20 万行随机采样（种子 42）   | A. 强行全量读入；B. 分块采样                                     | 选 B。8.4 GB 超过内存，分块 + 固定种子兼顾可运行性与可复现性。同时明确记录假设：采样代表性留待阶段二用全量统计验证                                           |
| 6 | Product 名称归一化           | A. 保留原始 20 类；B. 合并新旧命名至 13 类                          | 选 B。同一产品在不同年代的命名不同，不合并会让模型学到"命名年份"这种伪模式                                                                   |
| 7 | Git 操作方式：GitHub Desktop | A. 命令行 git；B. GitHub Desktop                          | 选 B。系统未安装命令行 git（"不是内部或外部命令"），而机器上已有 GitHub Desktop，图形界面可以完成提交、推送、打标签全部需求                                 |
| 8 | 原始数据入库问题                | A. 提交 8.4 GB 到 GitHub；B. gitignore 排除 + README 记录复现方法 | 选 B。GitHub 单文件限制 100 MB，大文件入库必然失败。排除原始数据并在 README 写明"运行 src/sample\_data.py 可重新生成样本"，同时满足可复现性要求           |

## 阶段二（2026-11-07）

| #  | 决策                                          | 当时的选项  | 我们的判断与理由 |
| -- | ------------------------------------------- | ------ | -------- |
| 11 | 时间划分 cutoff：2023-12-31 / 2024-01-01 | A. 按年份 70/30；B. 按最近 2 年做测试集 | 选 A（实为 28.5%/71.5%）。cutoff 选在 2023→2024 的自然年边界，训练集 445 万行（2011-12 ~ 2023-12-31），测试集 1116 万行（2024-01-01 ~ 2026-07-03）。测试集大是为了让 Bootstrap CI 有足够精度；训练集不含 2024+ 是为了彻底消除时间泄漏 |
| 12 | Bootstrap CI 实现方式：多项分布 vs 逐行重抽样 | A. 逐行重抽样 1100 万行 × 1000 次；B. 多项分布抽样 9 个格子 | 选 B。重抽样 N 个 (y_true, y_pred) 对后混淆矩阵各格子计数服从 Multinomial(N, p)，与逐行 Bootstrap 分布完全等价。numpy Generator.multinomial 用序贯二项法是 O(k) 而非 O(N)，实测 1000 次 0.13 秒，逐行重抽样需约 180 秒 |
| 13 | 评估函数：单次 confusion_matrix vs 4 次 sklearn 调用 | A. 复用 prototype.evaluate（classification_report + confusion_matrix + f1_score×2）；B. 自写 evaluate_efficient，只调用一次 confusion_matrix | 选 B。prototype.evaluate 在 1100 万行上调用 4 个 sklearn 函数，每个都做一次完整标签编码，合计约 178 秒/基线 × 3 基线 = 534 秒，超出时限被 SIGTERM。自写版只做 1 次标签编码（22 秒），其余 precision/recall/F1 从 3×3 矩阵瞬时推导，输出格式与 prototype.evaluate 完全一致。三基线总用时从 ~534 秒降至 ~75 秒 |
| 14 | category dtype + groupby 的 observed 坑 | A. 忽略 FutureWarning 用默认 observed=False；B. 显式 observed=True + TARGET 转字符串 | 选 B。parquet 的列是 category dtype，`.values` 返回 Categorical 对象使 TARGET 保持 category。groupby 默认 observed=False 时只要有一个 categorical grouper 就会对**所有** grouper 做全交叉积——P×I×C 产生 15×178×6767×3 ≈ 5400 万中间行（而非实际 6.1 万组合），直接撑爆内存。两重修复：① `.astype(str)` 把 TARGET 转成 object；② `observed=True` 显式只保留观测组合 |
| 15 | 时间划分基线结果解读：P×I 查表反而上升 | A. 全线下降才合理；B. P×I 上升有合理原因 | 选 B。时间划分下三基线 F1 = 0.2496 / 0.3361 / 0.4797。多数类下降 3.69%（测试集 explanation 占比从 72.7% 降到 59.9%）；P×I 查表反升 25.44%——随机划分下 P×I 查表在 20 万样本上只比多数类好 0.0087，全量时间划分下 Product×Issue 的多数类映射更稳定，non-monetary 的 recall 从 0 提到 0.177；P×I×C 查表下降 8.21%——公司维度的处理策略在 2024 年后有漂移（monetary 类几乎消失，recall 仅 0.067）。Bootstrap CI 极窄（宽度 ~0.001）是因为测试集 1100 万行，抽样变异极小 |
| 16 | 全量聚合引擎：DuckDB vs pandas 分块 | A. 继续 pandas 分块（阶段一的方式扩展到全量）；B. 换用 DuckDB 单遍扫描 | 选 B。9 组不同维度的分组聚合在 pandas 分块里要维护 9 套累加器、代码长且容易写错；DuckDB 把 CSV 一次性转成 158 MB 的列式 parquet 缓存后，每组聚合都是一条 SQL 的 GROUP BY，逻辑与结果都更好核对。关键是 Consumer complaint narrative 含换行（1654 万记录摊成 2766 万物理行），DuckDB 单线程 RFC4180 解析器能正确处理跨行记录而分块按行切分必然出错。内存上限硬控（2 GB）+ temp_directory 溢写，峰值稳定在 2.0 GB |
| 17 | 时间划分替代随机划分（消除时间泄漏） | A. 继续随机 80/20；B. 按 Date received 切时间 | 选 B。随机划分下同一家公司的历史与未来投诉被分到两侧，模型等于提前知道公司往后会怎么处理——时间泄漏。时间划分（2023-12-31 / 2024-01-01 边界）让测试集完全晚于训练集，消除泄漏。代价是分布漂移：三主类占比 训练 72.7%/24.0%/3.3% → 测试 59.9%/39.6%/0.6%，但这个漂移是真实的业务变化，不应当成 bug 隐藏。cutoff 的具体选位见 #11 |
| 18 | 清洗逻辑单点化：cleaning.py 唯一实现 | A. prototype.py 和 split_temporal.py 各自维护清洗；B. 抽取公共 cleaning.py 供两者导入 | 选 B。prototype.py（样本基线）与 split_temporal.py（全量时间划分）的清洗步骤完全相同（三主类筛选 / Complaint ID 去重 / Product 归一化 / 空值填充），如果各自维护一份，改一处忘另一处必然漂移。cleaning.py 导出 TARGET / TARGET_CLASSES / FEATURES / PRODUCT_NORMALIZATION 常量和 clean_data 函数，所有脚本从这里取，确保训练集与测试集用同一份规则清洗 |
| 19 | 准备加入 GroupKFold 对照 | A. 只做时间划分一种；B. 增加按公司分组的 GroupKFold | 计划选 B。EDA 发现测试集 99.85% 的行来自训练集已见过的公司（投诉量前 10 的公司 10/10 都见过），时间划分消除了时间泄漏但没消除「公司记忆」——模型可能只是在查表而非泛化。下一步计划按 Company 做 GroupKFold，让训练集与验证集的公司完全不重叠，测真正的跨公司泛化能力。这是阶段三的对照实验，不替代时间划分作为主评估 |
| 20 | 文档校对修正与依赖补全 | A. 校对发现问题搁置不动；B. 逐项修正并记入决策日志 | 选 B。独立校对发现 4 处文档错误：①三大征信局处理策略"高度一致"表述不实（TransUnion/Equifax 以 non-monetary relief 为主，Experian 以 explanation 为主，仅 monetary relief 均接近 0 这一点一致，原误称三家 non-monetary 占 49%～59%）；②目标变量口径错位（5 个非主类共 653,730 行，连同无目标值行合计 928,186 行，原误称 5 类共 928,186 行）；③缓存 parquet 行数误记为 16,270,799 有效行（实为 16,545,376 原始行，过滤在 split_temporal.py 中完成）；④Product 归一化影响行数误记约 268 万（精确 2,629,913，约 263 万）。另修正决策日志 #15 F1 0.4796→0.4797、#12 实测耗时 <0.1 秒→0.13 秒。requirements.txt 补 pyarrow==26.0.1、matplotlib==3.11.2（独立环境复现缺这两项跑不起来）。这正是决策日志存在的意义——记录演进中的修正而非掩盖错误。修正后 54 个 pytest 测试仍全绿 |
